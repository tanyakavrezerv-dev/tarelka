# «Тарелка» - пошаговый план разработки с нейросетью

Основание - [ТЗ учебного MVP v2](tarelka-course-mvp-v2.md).

Статус - план работ, код по этому плану ещё не реализован и проверки не выполнены. Срок не ограничен, обязательного технологического стека у курса нет.

## 1. Как работать с этим планом

Каждый шаг отдаём нейросети отдельным заданием. Один шаг должен завершаться небольшим проверяемым изменением. Если шаг слишком велик для одного сеанса, разделяем его по перечисленным подзадачам.

Порядок работы:

1. прочитать ТЗ, текущий шаг и результаты предыдущего;
2. посмотреть реальные файлы проекта;
3. реализовать только текущую задачу;
4. выполнить автоматические проверки, указанные в шаге;
5. показать результат в браузере, если появился интерфейс;
6. записать, что проверено и что осталось непроверенным;
7. сохранить рабочую версию в Git;
8. переходить дальше после устранения обнаруженных ошибок.

Успешный тест формулы не подтверждает работу кнопки. Наличие кнопки не подтверждает сохранение данных. Красивый экран не является признаком завершённой бизнес-логики.

Для каждого шага вести запись в `docs/progress.md` с полями:

- номер и статус - не начат, в работе, проверен, требует исправления;
- изменённые файлы;
- выполненные команды и результаты;
- ручные проверки;
- ограничения;
- идентификатор коммита, если он создан.

Нейросеть не должна отмечать проверку выполненной, если только прочитала код или написала тест, но не запускала его.

## 2. Общая инструкция для нейросети

Этот блок можно добавлять перед заданием каждого шага.

> Прочитай tarelka-course-mvp-v2.md, tarelka-implementation-plan.md и docs/progress.md, если он существует. Выполни только указанный шаг. Сначала проверь текущее состояние файлов. Не считай предыдущие ответы доказательством реализации. Не добавляй функции будущих этапов, внешние сервисы или новые библиотеки без обоснования. Расчёты должны быть отделены от DOM и хранения. Не подменяй неизвестные значения нулями. Не используй демонстрационные данные как подтверждённые факты. При противоречии опиши его и предложи конкретное решение. Выполни проверки шага и сообщи их фактические результаты. Не переписывай исправные модули ради изменения стиля. Обнови журнал прогресса. В итоговом ответе укажи, что сделано, как открыть результат и что ещё не проверено.

Дополнение для отдельной проверки:

> Проверь реализацию шага N по критериям этого плана. Сначала воспроизведи сценарии. Для каждого дефекта укажи входные данные, действие, ожидаемый и фактический результат. Не расширяй функциональность и не заменяй проверку общими замечаниями о качестве кода.

**Готово, когда** запуск воспроизводится по инструкции и тестовый инструмент действительно обнаруживает ошибки.

## Шаг 2. Зафиксировать контракт данных

**Задание нейросети**

> Опиши и реализуй проверку структуры состояния по ТЗ v2. Подготовь маленькие искусственные данные для тестов. Полный каталог пока не создавай.

**Сделать**

- разделить режим продажи и базовую единицу;
- описать schemaVersion, seedVersion, revision и operationId;
- зафиксировать, что готовый вес относится к полному базовому рецепту, а вес порции является отдельным полем;
- предусмотреть снимок расхода завершённого дня для корректной отмены;
- проверять ссылки на продукты, уникальность идентификаторов, единицы, допустимые числа;
- определить пределы импортируемых коллекций, размера файла и чисел, явно назвав их техническими ограничениями учебной версии.

**Как проверить**

- корректный минимальный набор проходит проверку;
- неизвестный productId, повтор id, отрицательная упаковка и нулевой выход отклоняются;

- ошибочный ввод возвращает понятную причину без частичной модификации состояния.

**Готово, когда** все следующие шаги используют один контракт из docs/data-contract.md.

## Шаг 3. Реализовать количества, деньги и календарные даты

**Задание нейросети**

> Реализуй независимые функции преобразования единиц, точности, отображения денег и местных календарных дат. Не подключай DOM или localStorage.

**Как проверить**

| Вход | Ожидаемый результат |
|---|---|
| 1,2 кг | 1200 г |
| 0,9 л | 900 мл |
| 0,5 г | 500 тысячных грамма |
| 0,5 шт | 500 тысячных штуки |
| мл в г без дополнительных данных | Ошибка несовместимости |
| 450 рублей | 45000 копеек |
| Дата 2026-10-13 | Понедельник 2026-10-12 |
| Дата 2027-01-01 | Понедельник 2026-12-28 |

Дополнительно проверить местные даты рядом с полуночью и границами месяца. Не получать календарную дату простым обрезанием UTC-строки. Функции принимают дату аргументом, чтобы тесты не зависели от дня запуска.

**Готово, когда** преобразования имеют явные границы округления и не смешивают г, мл и шт.

## Шаг 4. Реализовать расчёт питания

**Задание нейросети**

> Реализуй КБЖУ и клетчатку отдельного продукта, рецепта, выбранной порции и дня. Используй искусственные контрольные данные; интерфейс не создавай.

**Как проверить**

| Сценарий | Ожидание |
|---|---|
| 200 ккал на 100 г, съедается 150 г | 300 ккал |
| 78 ккал на штуку, количество 0,5 шт | 39 ккал |
| 1700 ккал на рецепт, выход 850 г, порция 320 г | 640 ккал |
| 1200 ккал на 4 порции, выбраны 3 | 900 ккал |
| Выход изменён только в одной записи | Другая запись и каталог не меняются |
| Выход неизвестен | Доступны порции; расчёт в граммах не выдаёт выдуманный итог |
| Известно 3 г клетчатки, у другого ингредиента null | Известная сумма 3 г с признаком неполноты |

Проверить все пять показателей, пустой день и несколько записей в одном приёме пищи. Вычисления не округляются до целых граммов нутриентов на каждом ингредиенте.

**Готово, когда** тесты подтверждают формулы и неполные данные обозначаются явно.

## Шаг 5. Реализовать потребность, упаковки и стоимость

**Задание нейросети**

> Построй расчёт потребности из меню и ручных продуктовых строк. Реализуй режимы продажи и стоимость по формулам ТЗ v2. Покупки и движения пока передавай как готовые входные данные.

**Сделать**

- агрегировать по productId, не по названию;
- использовать тот же масштаб рецепта, что в КБЖУ;
- вычислять R и T с учётом расхода C и баланса B;
- отделить стоимость меню от покупок;
- поддержать упаковку, вес/объём, штуки и свободную строку;
- округлять деньги один раз на строку;
- сохранять неполные итоги при строках без цены.

**Как проверить**

- 500 + 300 г одного продукта дают 800 г;
- разные варианты молока не объединяются;
- 1000 г потребности минус 400 г дома дают 600 г;
- 700 г при упаковке 900 г дают одну упаковку; 901 г дают две;
- 0,5 шт для питания дают покупку одной штуки;
- 250 г по цене 180 рублей за кг дают 45 рублей;
- 700 г при упаковке 900 г за 450 рублей дают меню 350 рублей и покупку 450 рублей;
- ручная продуктовая строка влияет на покупки, но не на питание;
- свободная строка имеет статус «без расчёта»;
- сумма двух строк по 0,5 копейки после округления каждой строки равна 2 копейкам;
- два одинаковых вызова не меняют исходное состояние.

**Готово, когда** расчёты можно проверить без браузерного интерфейса.

## Шаг 6. Реализовать журнал и покупку

**Задание нейросети**

> Реализуй команды покупки, отмены покупки и корректировки остатка. Возвращай новое состояние целиком или ошибку. Не сохраняй изнутри расчётных функций.

**Сделать**

- отдельную запись покупки и движение кладовки;
- снимок цены покупки;
- защиту от повторного operationId;
- возможность второй законной покупки того же продукта с новым operationId;
- внешнюю покупку без пополнения кладовки;
- обратное движение при отмене;
- исправление остатка через разницу балансов.

**Как проверить**

1. При N = 700 г купить 900 г - B = 900 г, T = 0, покупка сохранена.
2. Повторить ту же операцию - баланс и запись не дублируются.
3. Увеличить N до 1100 г - T = 200 г, первая покупка видна.
4. Купить ещё 900 г новой операцией - B = 1800 г, две покупки.
5. Удалить меню - обе покупки сохраняются.
6. Отменить одну покупку - B = 900 г, активна одна покупка.
7. Исправить B с 900 до 100 г - движение равно минус 800 г.
8. При N = 700 г после корректировки T = 600 г.
9. Внешняя покупка не увеличивает B и не уменьшает T.
10. Отмена, создающая отрицательный баланс, отклоняется без частичных изменений.

**Готово, когда** ни покупка, ни пересчёт не теряют историю и не удваивают запас.

## Шаг 7. Реализовать завершение дня и переопределения

**Задание нейросети**

> Реализуй подтверждённое списание дня, его отмену и ручное количество следующей покупки. Проверяй их вместе с уже готовым ядром.

**Как проверить**

- при N = 700, B = 900 завершение дня с 300 г даёт C = 300, B = 600, R = 400, T = 0;
- повторное завершение не меняет состояние;
- завершённый день нельзя редактировать;
- отмена возвращает ровно сохранённый расход, C = 0 и B = 900;
- при недостатке одного ингредиента не списывается ни один ингредиент дня;
- увеличение будущей потребности до N = 1100 при C = 300 и B = 600 даёт T = 200;
- ручное количество сохраняется после пересчёта, отличие от рекомендации видно;
- «Вернуть расчёт» удаляет переопределение;
- покупка использует переопределение один раз, после неё оно снято;
- для упаковочного товара переопределение задаёт число упаковок, а не произвольную несовместимую массу.

**Готово, когда** полный цикл из ТЗ проходит в автоматических тестах до появления кнопок.

## Шаг 8. Реализовать сохранение, восстановление и импорт

**Задание нейросети**

> Добавь адаптер localStorage и единый порядок применения команд. Проверь ошибки хранения и импорта через подставное хранилище, затем в браузере.

**Сделать**

- прочитать и проверить состояние;
- рассчитать новое состояние командой;
- проверить и сохранить его целиком;
- только после успешного сохранения принять изменение в интерфейсе;
- обрабатывать несовпадение revision;
- не перезаписывать повреждённые или неизвестные версии;
- проверять импорт до замены;
- экспортировать пользовательское состояние вместе с версиями и необходимыми снимками;
- сбрасывать только ключи проекта.

**Как проверить**

1. Сохранить покупки и расход, загрузить заново - баланс, C и суммы совпадают.
2. Смоделировать отказ записи - успех не сообщается, прежнее состояние сохранено.
3. Загрузить битый JSON - исходная строка не перезаписана seed.
4. Загрузить неизвестную версию - предложено восстановление или явный сброс.
5. Импортировать неверные ссылки, слишком большой файл и неверные типы - отказ без потери данных.
6. Экспортировать и импортировать исправный файл - бизнес-данные совпадают, служебная revision может измениться.
7. Добавить чужой ключ в хранилище, сбросить демо - ключ остаётся.
8. Открыть вторую вкладку, изменить первую, попытаться сохранить устаревшую вторую - запись блокируется до перечитывания.

Одновременное редактирование нескольких вкладок не объявлять поддержанным. Проверка revision предназначена для обнаружения устаревшего состояния, а не является полноценной синхронизацией.

**Готово, когда** ошибка сохранения не выглядит как успех и не уничтожает рабочие данные.

## Шаг 9. Подготовить каталог и воспроизводимое демо

**Задание нейросети**

- все цены пометить демонстрационными;
- добавить фрукты, хлеб, йогурты и напитки напрямую как продукты;
- подготовить текущую неделю из смещений относительно понедельника;
- обеспечить видимые свободные слоты;
- контрольный продукт должен иметь суммарную потребность ровно 700 г, упаковку 900 г и цену 450 рублей;

**Как проверить**

- число продуктов измерено, а не указано приблизительно в отчёте;
- одинаковая дата даёт одинаковое содержание демо;
- дата на границе года даёт правильную неделю;
- контрольные 700/900/300 г подтверждены расчётом всего меню;
- записи источников действительно открыты и проверены, отсутствующие источники обозначены;
- размер сериализованного состояния измерен.

**Готово, когда** демо использует общие формулы приложения, без специально подставленных итогов.

## Шаг 10. Собрать интерфейс недели и каталога

**Задание нейросети**

> Подключи готовое ядро к экрану недели и каталогу. Формулы не дублируй в обработчиках кнопок. Используй безопасный вывод текстовых полей.

**Сделать**

- пять приёмов пищи и несколько записей в каждом;
- добавление рецептов и продуктов;
- поиск, изменение порции, удаление записи;
- ввод готового веса полного рецепта и веса порции с разными подписями;
- дневные итоги, цели, неполную клетчатку;
- на телефоне переключение всех семи дней;
- исключить переключение на новые недели, не входящее в текущий MVP.

**Как проверить вручную**

1. Добавить кашу и банан в один завтрак - обе записи видны и учтены.
2. Изменить порции - итог меняется согласно тестам ядра.
3. Выбрать граммы готового блюда - ввод не смешивается с сырым весом.
4. Удалить одну запись - соседняя остаётся.
5. Обновить страницу - изменения сохранены.
6. На узком экране открыть каждый из семи дней, включая воскресенье.
7. Ввести отрицательное значение - получить понятную ошибку.

**Готово, когда** пользователь планирует меню без ввода внутренних productId и без консоли браузера.

## Шаг 11. Подключить список покупок

**Задание нейросети**

> Реализуй экран покупок на основе расчётных строк и сохранённых покупок. Покажи все переходы, предусмотренные ТЗ.

**Сделать**

- отдельные разделы купленного и предстоящих покупок;
- магазины и категории;
- стоимость меню, куплено, осталось купить, общий бюджет;
- изменение количества, заметки и магазина;
- ручную продуктовую строку и свободный текст;
- внешнюю покупку и отмену;
- копирование списка с понятным запасным способом выделить текст, если копирование недоступно.

**Как проверить вручную**

- пройти 700 -> купить 900 -> увеличить до 1100 -> уменьшить до 700;
- первая покупка не исчезает, дефицит и дополнительная упаковка меняются;
- отмена покупки меняет запас и итоговую стоимость;
- ручное количество сохраняется при изменении меню;
- свободная строка не получает выдуманную цену и не попадает в КБЖУ;
- смена магазина меняет группу, но не цену;
- скопированный текст соответствует видимому списку;
- подпись «демонстрационные цены» видна возле денежных итогов.

**Готово, когда** итог «куплено + осталось купить» сохраняется корректным после всех действий.

## Шаг 12. Подключить кладовку и завершение дня

**Задание нейросети**

> Добавь экран остатков, журнал и интерфейс подтверждения расхода. Используй существующие команды, не создавай отдельную логику списания в UI.

**Как проверить вручную**

1. Купить продукт - положительное движение видно в журнале.
2. Изменить остаток с 900 до 100 г - видна корректировка минус 800 г.
3. Попытаться завершить день при нехватке - увидеть перечень недостающего, баланс не изменён.
4. Пополнить запас и завершить день - расход списан один раз.
5. Попытаться изменить завершённый день - предложена отмена завершения.
6. Отменить завершение - остаток восстановлен.
7. Попытаться отменить покупку, если это создаёт отрицательный баланс - операция отклонена с объяснением.

**Готово, когда** любое изменение баланса можно объяснить записями журнала.

## Шаг 13. Подключить настройки, резервную копию и сброс

## 5. Шаблон отчёта нейросети

```text
шаг - номер и название
статус - проверен / требует исправления
сделано - конкретные изменения
файлы - перечень
автоматические проверки - команды и фактический результат
ручные проверки - действия и наблюдения
не проверено - конкретные ограничения
как посмотреть - адрес или команда
следующее действие - следующий шаг или исправление
```

Не принимать формулировки «должно работать», «всё готово» или «тесты предусмотрены» вместо результатов запуска. Не просить нейросеть написать весь продукт одним запросом. Основной способ удержать качество - маленькие задачи, числовые примеры и проверка сохранённого результата после каждого значимого перехода.
